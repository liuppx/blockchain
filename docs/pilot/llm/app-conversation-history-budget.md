# 按词元预算管理对话历史

| 字段 | 内容 |
|---|---|
| 层级 | 应用 |
| 主题 | 提示与上下文 |

| 版本 | v2 |
| 语言 | zh |

## 核心陈述

自己开发对话应用时,每次请求前都要决定"把多少历史放回上下文"。对只含用户与助手消息的简单对话,
可以固定保留系统提示和本次问题,给回答预留额度,再从最近的完整问答轮次往前装,装不下就停止。
包含工具调用、多模态内容或服务端会话状态的应用,需要按实际消息结构和接口限制扩展预算逻辑。

## 正文

### 怎么做

1. 按模型与接口文档确认这次请求适用的输入预算 `input_budget` 和计量方式。若接口有共享的上下文预算,
   先从中扣除所需的输出预留;若输出上限单独计算,按接口规则独立检查,不要重复扣减。
2. 使用对应模型的 tokenizer 和消息格式计量系统提示、本次问题与结构开销。如果这一步已超过输入预算,
   应报告超限或请求缩短,而不是悄悄截断。
3. 把历史按"一问一答"分成轮,**从最近的一轮往前**逐轮加入,直到预算用完。
4. 按时间顺序拼回:系统提示 → 保留的各轮 → 本次问题。
5. 记录丢掉了几轮(写日志或提示用户),方便排查"模型怎么不记得了"。

下面是一个只用标准库的最小示意,仅适用于文本消息、简单的一问一答历史。示例用 UTF-8 字节数近似正文长度,
用固定常数近似消息格式开销,不能替代接口对应的 tokenizer 或官方计量规则(在 Python 3.12 上运行验证,2026-11):

```python
def count_tokens(text):
    """替换为你所用模型的分词器。UTF-8 字节数只作示意估算,不代表接口实际词元用量。"""
    return len(text.encode("utf-8"))

PER_MESSAGE_OVERHEAD = 8  # 每条消息的角色标记等开销,因模型而异,宁大勿小

def msg_tokens(m):
    return count_tokens(m["content"]) + PER_MESSAGE_OVERHEAD

def fit_history(system, history, question, input_budget):
    """在已计算好的 input_budget 内装下系统提示、最近问答轮次和本次问题。
    history 必须是 [user, assistant, user, assistant, ...]。返回 (messages, 丢掉的轮数)。"""
    fixed = [{"role": "system", "content": system}, {"role": "user", "content": question}]
    budget = input_budget - sum(msg_tokens(m) for m in fixed)
    if budget < 0:
        raise ValueError("系统提示 + 问题 已超出输入预算,请缩短它们")
    turns = [history[i:i + 2] for i in range(0, len(history), 2)]  # 一问一答为一轮,整轮保留或整轮丢弃
    kept = []
    for turn in reversed(turns):  # 从最近的一轮往前装
        cost = sum(msg_tokens(m) for m in turn)
        if cost > budget:
            break
        kept.insert(0, turn)
        budget -= cost
    msgs = [fixed[0]] + [m for t in kept for m in t] + [fixed[1]]
    return msgs, len(turns) - len(kept)

if __name__ == "__main__":
    hist = []
    for i in range(1, 7):
        hist += [{"role": "user", "content": f"第{i}个问题" + "。" * 40},
                 {"role": "assistant", "content": f"第{i}个回答" + "。" * 40}]
    msgs, dropped = fit_history("回答一律用中文。", hist, "总结一下我们聊了什么", input_budget=900)
    used = sum(msg_tokens(m) for m in msgs)
    print(f"保留 {len(msgs)} 条消息,丢掉最早的 {dropped} 轮,估算占用 {used}(预算 900)")
    print("第一条:", msgs[0]["role"], "| 最早保留:", msgs[1]["content"][:4], "| 最后一条:", msgs[-1]["content"])
    assert msgs[0]["role"] == "system" and msgs[-1]["content"] == "总结一下我们聊了什么"
    assert used <= 900
```

### 为什么

- **为什么必须做这件事**:模型不保存对话,历史只能由应用每次重新发送;而上下文窗口有上限,历史迟早会放不下。
- **为什么按词元而不是按字数或条数**:窗口按词元计算;字数与词元数的换算因分词器和语言而异,按条数更是完全不可控。
- **为什么按接口规则预留额度**:模型窗口、输入限制和最大输出限制的关系因接口而异。按文档计算并留足输出额度,可减少请求被拒绝或回答被截断。
- **为什么固定保留系统提示**:重要的约定放在系统提示里,才不会随着历史增长被截掉。
- **为什么整轮保留**:只留下回答而丢掉对应的问题(或反过来),模型会看到断裂的上下文,容易误解。
- **为什么从最近的往前装**:多数对话中,最近的内容与当前问题最相关。

### 常见错误

| 错误 | 为什么会出错 | 怎么纠正 |
|---|---|---|
| 用字节数或字数代替接口实际词元用量 | 换算关系因语言、tokenizer、消息格式与模态而异 | 优先使用所用模型和接口提供的 tokenizer 或计量方法;估算时预留余量并用响应 usage 对照 |
| 不按接口规则给回答留额度 | 输出限制与上下文窗口的关系因接口而异 | 按对应接口文档预留输出额度 |
| 系统提示放在历史里一起截断 | 最早的消息最先被丢掉,约定随之失效 | 系统提示单独处理,永远保留 |
| 超出时让接口自己截断 | 不同接口超出时的行为不同,可能直接报错,也可能截掉你不想丢的部分 | 发送前自己控制 |
| 悄悄丢弃、不留记录 | 用户和开发者都不知道模型为什么"忘了" | 记录丢掉的轮数,必要时提示用户 |

## 自己验证

把上面的代码存为 `history.py` 直接运行(`python3 history.py`)。示例估算输出如下,计量单位是代码定义的近似值,不是 API 实际 token 用量:

```
保留 6 条消息,丢掉最早的 4 轮,估算占用 634(预算 900)
第一条: system | 最早保留: 第5个问 | 最后一条: 总结一下我们聊了什么
```

然后把 `count_tokens` 与 `msg_tokens` 换成适用于你所用接口的计量逻辑,用真实请求与接口返回用量对比。
不要假定固定的每消息开销足以形成上界,也不要仅凭估算值断定请求一定能放入上下文。

## 适用范围与局限

- 适用:文本消息、用户与助手交替发言的简单多轮对话,作为裁剪策略示意。
- 不适用 / 会失效的情况:早先内容对当前问题至关重要时,简单截断会丢掉关键信息,
  需要配合摘要旧内容、或检索相关的历史片段(待补应用单元)。
- 容易过时的部分:各模型的窗口大小与消息格式开销;部分接口开始提供服务端的历史管理。
- 默认的 `count_tokens`(UTF-8 字节数)不是 API token 用量保证;消息格式开销常数也只是示例。多模态输入、工具调用、结构化输出和服务端会话都需要额外计量或不同的消息分组。

3. 一轮只按"一问一答"切分;确认工具调用、多模态和服务端会话状态已列为需要扩展的情况。
4. 核实示例预算与所用 API 的输入和输出限制分开说明,没有假设所有接口共用一个额度。
