## 核心陈述

聊天产品里的"忘记"是用户观察到的现象,可能由多种原因造成。后续推理可能没有获得早先信息,因为应用或服务端
截断、摘要或检索了历史;信息也可能仍在上下文中,但模型没有正确遵循、提取或利用它。排查时应先检查实际发送或关联的
会话状态,再区分上下文缺失与模型在已有上下文中的表现。

## 正文

### 一个常见的困惑

和聊天助手讨论了一个下午,开头约定的规则("回答一律用表格"、"我的项目用的是 Python 3.9")
后来不再被遵守,好像它忘了。

### 实际发生了什么

可以从三个层次排查:

1. **确认历史是否进入当前会话。** 应用可能在客户端发送消息历史,也可能使用服务端会话。应检查请求、会话 ID 和接口状态管理方式。
2. **检查历史如何被管理。** 上下文与接口都有长度限制。系统可能采取以下一种或多种方式:
   - 丢掉最早的几轮;
   - 把旧内容压缩成一段摘要(摘要难免丢细节);
   - 只挑出与当前问题相关的片段放回去。
   因此,早先内容可能没有进入当前上下文,或只以摘要与检索结果的形式出现。
3. **检查模型是否正确利用已提供的信息。** 即使信息仍在上下文里,模型也可能受位置、干扰信息、后续冲突指令或自身能力限制,
   没有遵循或准确回忆它。回答错误本身不能证明信息已从上下文移除。

### 那该怎么办

- **重要约定使用明确的应用策略管理**:按接口要求将其置于稳定的指令位置或受控的外部状态中,并检查组装后的实际请求;仍需测试模型是否遵循。
- **长任务分段**:一个阶段结束后,开新对话,把需要延续的结论整理好放在开头。
- **区分缺失与未遵循**:查看客户端请求或服务端会话状态,确认信息是否存在,再测试模型能否正确使用。

如果你在开发自己的应用,"历史怎么截"就是你要设计的东西,见应用单元
[按词元预算管理对话历史](app-conversation-history-budget.md)。

## 自己验证

在自己可检查请求与会话状态的聊天应用中,记录一条随机生成且不易猜到的约定或事实,然后增加历史长度。
在每个阶段检查服务端会话或最终请求中是否仍包含原信息,同时用固定问题测试模型能否回答。另开独立会话重复测试,
并记录模型版本、提示、历史长度和会话管理配置。

预期:实验可能观察到历史被移除或摘要、信息仍存在但模型未能使用,也可能始终正确。该实验用于定位特定应用中的行为,
不能只凭回答错误推断上下文缺失,也不能推广到其他产品。

## 适用范围与局限

- 适用:排查聊天应用为何没有按预期利用早先对话信息。
- 不适用:仅凭用户侧回答就断定服务端是否保存、截断或检索了哪些历史。
- 容易过时的部分:各产品的具体截断与记忆策略。

## 核验要点(给人类审查者)

1. 确认用户看到的失败没有被直接归因于历史截断,且包括模型没有正确利用仍在上下文中的信息。
2. 自测能否查看真实请求或会话状态,使用无法轻易猜到的随机事实,并记录模型与历史管理配置?
3. 是否纳入后续冲突指令、干扰上下文和模型指令遵循能力等其他原因?
