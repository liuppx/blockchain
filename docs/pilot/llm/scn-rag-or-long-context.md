# 资料太多放不进上下文:检索增强,还是直接用长上下文

| 字段 | 内容 |
|---|---|
| 层级 | 场景 |
| 主题 | 检索与知识 |
| 来源 | 模型生成(Claude Opus 5.5) |
| 状态 | **待核验** |
| 版本 | v2 |
| 语言 | zh |

## 核心陈述

要让模型基于你自己的资料回答问题,可以把相关资料放进上下文,也可以先用检索系统找出候选片段再提供给模型
(检索增强生成,RAG)。两者可以组合。资料量和问题类型会影响设计,但不能单独决定哪种方案更准确、更省或更可靠。
应结合任务质量、资料更新、权限、安全、延迟与端到端成本进行实测。

## 正文

### 处境

你有一批资料:产品文档、公司制度、代码库、几百份合同……希望模型基于它们回答,而不是凭训练时的印象。
模型训练时没见过这些资料,也不会因为对话而学会它们,所以资料必须在回答时放进上下文。

### 两种做法

| | 直接放进长上下文 | 检索增强生成(RAG) |
|---|---|---|
| 做法 | 请求时把一组相关资料与问题一并提供 | 先检索候选资料,再把选中的片段与问题提供给模型;检索可用关键词、向量或混合方法 |
| 前提 | 所提供内容和问题适合当前模型与接口的输入限制 | 需要建立并维护索引、检索、权限过滤和更新流程 |
| 可能适用 | 需要跨多份资料综合理解,且候选资料集能够筛到可用范围 | 答案可能位于少量资料片段,或需要控制每次提供的资料范围 |
| 主要风险 | 输入过长会增加处理负担;部分模型在长上下文不同位置的信息利用可能不均 | 检索漏召回或排序不佳时,所需依据不会进入上下文;错误权限过滤还可能暴露不该提供的资料 |
| 资料更新 | 请求组装时可以纳入最新内容,仍需确认数据来源与时间 | 索引可能滞后,需监控更新延迟、删除传播和索引一致性 |
| 证据与权限 | 应记录资料来源,并按用户权限筛选可提供内容 | 应在检索前或可靠的检索阶段执行权限过滤,并记录命中的来源与版本 |
| 成本与延迟 | 受输入长度、缓存、模型价格和请求频率影响 | 另有索引构建、存储、检索和运维成本,总成本取决于流量及实现 |

### 怎么判断

1. **先明确任务和约束**:准备代表性问题、正确答案、引用依据、无答案问题和各用户权限。
2. **比较候选流程**:可包括直接提供资料、关键词检索、向量检索和混合检索,不要把 RAG 等同于只用嵌入。
3. **测量质量**:记录答案正确性、依据是否支持答案、引用准确性、拒答表现和不同权限用户之间的数据隔离。
4. **测量运行特征**:记录端到端延迟、输入与输出用量、检索成本、索引更新延迟和维护成本。缓存会改变重复请求的开销。
5. **按需求选择或组合**:先检索筛候选资料,再把候选片段放进长上下文,也是一种可评估的设计。

### 不管选哪个都要做的事

- **准备带标准答案和出处的问题集**,区分可回答问题与资料中无答案的问题;
- **核对引用是否确实支持答案**,单让模型自报来源不足以验证引用;
- **使用相同模型、提示、输出限制和评估条件比较方案**,记录版本并对非确定性输出重复测试;
- **对权限要求构造不同用户的问题**,确认任何方案都不会把越权资料放进模型上下文。

## 自己验证

从真实使用中抽取一组代表性问题,其中包括无答案问题、需要综合多份资料的问题和不同权限用户的问题。
对每个问题运行多个候选流程,必要时重复请求,记录答案正确性、依据支持度、引用准确性、拒答、越权命中、
端到端延迟、模型用量、检索与索引成本、资料更新延迟。

预期:结果取决于资料、任务、模型、提示和实现。实验应报告问题数量、重复次数、评估方法与失败案例;
不要从一次小样本对比推广出通用的准确率、成本或延迟结论。

## 适用范围与局限

- 适用:基于私有资料的问答、客服、文档助手。
- 不适用:需要改变模型的语气、格式或掌握一种新技能的场景,这更接近微调要解决的问题(待补单元)。
- 容易变化的部分:模型可用上下文、接口限制、价格、检索工具和索引服务都会变化,需按当前目标服务重新评估。

## 核验要点(给人类审查者)

1. 核对对比表是否把检索实现过度简化为向量嵌入,或把权限控制误写成检索天然保证。
2. Lewis et al. (2020) 的 RAG 是特定的检索器与生成器方法;确认没有把论文实验结论泛化到所有现代 RAG 实现。
3. 确认成本与质量结论要求目标任务上的测量,而不是从语料大小直接推断。
4. 检查权限隔离、删除传播、索引更新和引用核验是否有明确测试办法。
