## 核心陈述

调用工具的智能体会在多轮过程中读取结果、选择后续行动并改变外部状态。评测应在隔离的可复位环境中运行代表性任务，并同时检查最终状态和关键执行约束。单看最终回答、一次成功样例或工具调用的字符串是否匹配，都不足以说明系统在真实使用中可靠。

## 正文

### 一个评测任务需要什么

每个任务至少包含:

- 初始条件与明确的用户目标;
- 智能体可以调用的工具及其权限;
- 可检查的成功条件和必须遵守的约束;
- 能由程序或人工复核的评分规则;
- 可重复的环境设置及复位方法。

例如,预订任务的成功条件应检查数据库或模拟环境中是否存在符合要求的预订,不能只检查模型是否回复“已预订”。如果任务要求先获得确认或禁止超预算,也应分别检查这些约束。

### 分开测量结果、过程与成本

至少保留以下几类指标,并报告各自的分母和样本量:

| 维度 | 可观察指标 | 例子 |
|---|---|---|
| 任务结果 | 满足最终状态条件的任务比例 | 预订的日期、航班及乘客均符合要求 |
| 约束与安全 | 越权读取、未经授权的写入、遗漏确认等违规次数 | 无确认时数据库中的预订记录数为 0 |
| 工具执行 | 无效调用、参数错误、重试、工具调用总数及串并行情况 | 两个独立查询能否并行完成 |
| 运行成本 | 每个成功任务的输入 / 输出词元、延迟和费用 | 同时报告中位数、尾部延迟及失败比例 |

不同任务的正确行动可能存在多种等价方案。只有当调用顺序或参数本身就是任务要求时,才将具体工具轨迹作为严格的成败标准。否则应以环境结果和必要约束为主,将轨迹指标用于诊断。

### 运行多轮且可重复的测试

1. 从生产请求、人工编写的边界案例和失败记录中建立任务集,包含正常、无答案、歧义、工具报错和权限边界情形。
2. 为每个任务保存独立环境快照,每次试验前复位,避免上一轮的状态污染下一轮。
3. 固定并记录模型与服务版本、系统提示、工具定义、权限配置、采样参数、超时和重试设置。
4. 对非确定性配置按预先确定的次数重复试验。报告每项任务的成功比例、汇总结果和分母,不要只报告最好的一次。
5. 检查结构化轨迹定位故障,人工复核自动评分器容易误判的样例。把有代表性的失败保留为回归任务。
6. 在更换模型、提示、工具或编排逻辑前后运行同一评测,报告质量、安全、延迟和成本变化。

评测任务的输入、评分标准和工具返回数据都应视为不可信内容。评测时应使用隔离的测试账户和可复位数据,不给样例任务连接真实付款、用户私信或生产写入能力。

### 本地示意

下面的评分器直接检查环境状态。它同时将越权副作用作为独立指标,所以“完成任务”不会抵消安全违规。

```python
def grade_task(state, expected_owner, expected_status):
    task_succeeded = any(
        order["owner"] == expected_owner and order["status"] == expected_status
        for order in state["orders"]
    )
    unauthorized_writes = sum(
        order["owner"] != expected_owner for order in state["orders"]
    )
    return {
        "task_succeeded": task_succeeded,
        "unauthorized_writes": unauthorized_writes,
    }

state = {"orders": [
    {"owner": "user-1", "status": "confirmed"},
    {"owner": "user-2", "status": "cancelled"},
]}
result = grade_task(state, "user-1", "confirmed")
assert result == {"task_succeeded": True, "unauthorized_writes": 1}
print(result)
```

示例预期输出为 `{'task_succeeded': True, 'unauthorized_writes': 1}`。此评分结果显示目标已完成,同时也存在一笔越权写入,应按安全失败处理。

## 对开发者意味着什么

1. 先写清用户可观察的成功条件与必须遵守的约束,再实现评分器。
2. 结果评分应尽可能读取外部系统最终状态、测试断言或人工判断,不只读取模型自述。
3. 分开报告正确性、安全、轨迹和资源指标,避免单个总分掩盖越权或有害副作用。
4. 记录导致结果的完整调用轨迹、工具返回、环境快照及版本信息,方便定位回归。
5. 用固定回归集阻止已知失败重现,并继续从真实失败中补充新任务。

## 适用范围与局限

- 适用:多轮工具调用、MCP 工具、编码智能体及会改变外部状态的助手。
- 不适用:把一个特定基准的分数直接解释成上线后的成功率或所有业务的性能排名。
- 需要按应用决定的部分:自动评分覆盖率、人工复核比例、重复次数与任务权重。

## 核验要点(给人类审查者)

1. 对照 Anthropic 原文核验任务、试验、评分器、轨迹和最终环境结果的定义,确认没有把一篇工程文章的建议表述成普适协议。
2. 阅读 MCPAgentBench 对 TFS 与 TEFS 的定义及局限。该基准的黄金调用集合与排序评分是特定基准设计,不自动适用于所有真实任务。
3. 运行示例并确认目标成功与越权写入可同时报告,且安全问题没有被单一总分掩盖。
4. 检查评测环境确实使用复位的测试数据,没有连接生产副作用。
