# 模型本身不保存对话

## 核心陈述

普通的模型推理不会因为一次请求而自动更新模型参数,所以模型权重本身不会把这次对话保存成新的长期记忆。
聊天应用若要在后续轮次继续利用对话信息,需要通过请求消息、服务端会话状态、外部存储或检索等方式提供相关上下文。

## 正文

### 一次对话在接口层面是什么样

调用对话接口时,应用可以把消息列表发送给服务,也可以使用由服务端维护的会话或响应状态。
无论历史由客户端还是服务端管理,生成时服务都要依据当前请求可用的上下文处理输入。具体历史如何存储、
截断、摘要或检索,取决于接口与应用实现,不应仅凭请求中是否重复包含消息列表判断模型是否保留了参数记忆。

如果一次独立请求只发"那它的首都呢?"且没有关联会话或其他上下文,模型就缺少"它"的指代依据。

### 模型的参数在对话中不会改变

模型的知识存在训练得到的参数里。普通的推理请求只读取参数,**不修改参数**。你在对话里告诉它的新信息,
请求结束后不会因此写入模型参数;要让后续请求使用这些信息,应用或服务需要保留会话状态、存到外部系统并取回,
或通过其他明确的记忆机制提供相关内容。

### 对开发者意味着什么

1. **对话历史需要由客户端或服务端管理**:是否每次由客户端重发完整消息、服务端如何保留或压缩状态,取决于接口设计。
2. **应用层记忆不是参数更新**:保存对话、摘要旧内容、检索历史片段,以及产品提供的记忆能力,都需由系统在后续推理中以某种方式提供。
3. **会话状态与提示缓存是不同能力**:提示缓存可能复用输入计算,会话接口可能替应用保存历史;应查清接口具体提供什么。
4. **不能只从模型回答判断它是否有上下文**:它可能从训练知识猜测或生成看似合理但错误的回答。应用应按接口文档管理会话与状态。

## 自己验证

用任意对话接口做两次请求(把 `call_model` 换成你所用的接口):

```python
def call_model(messages):
    """替换为你所用模型的接口调用,返回回答文本。"""
    raise NotImplementedError

# 第一次:在无状态请求中带上前文
print(call_model([
    {"role": "user", "content": "我最喜欢的数字是 17。"},
    {"role": "assistant", "content": "好的,记住了。"},
    {"role": "user", "content": "我最喜欢的数字是多少?"},
]))
# 第二次:发起新的独立请求,不复用会话 ID,也不带前文
print(call_model([{"role": "user", "content": "我最喜欢的数字是多少?"}]))
```

预期:第一次可依据给定消息回答 17;第二次没有该信息的上下文依据,可能说不知道,也可能猜测或编造答案。
若使用会话 ID、服务端历史或产品记忆功能,需查清它们是否向第二次推理提供了前文,否则这不是独立请求对比。

## 适用范围与局限

- 适用:通过接口调用的大语言模型推理。
- 不适用:在线学习、持续微调等会更新参数的场景(不在普通推理请求中发生)。
- 容易过时的部分:各厂商的会话管理、提示缓存、记忆功能的具体形式。

## 核验要点(给人类审查者)

1. 核对“权重不会自动记住请求”与服务端会话状态的区别是否讲清楚。
2. 按接口文档确认服务端会话可能使用的保留、截断、摘要和检索策略，不推断其内部实现。
3. 运行示例时确认第二次调用是真正独立请求，并提醒读者模型可能猜测或编造。
4. “推理不自动更新权重”的论断仍需补充适当的教材或官方技术出处。
