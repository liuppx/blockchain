# 知行图试运行方案 v0.1

> 状态:草案,待确认(见文末「需要决定的事」)。对应 VISION §4b「参数须在试运行中实测」与 Q8「下一步起草试运行方案」。

## 1. 为什么要试运行

四轮仿真(`sim/convergence.py`,结论见 VISION §4b)说明了机制**在什么条件下**能让质量收敛,
但决定安全的三个参数在模型里都是**假设**,从没测过:

| 参数 | 仿真里的假设 | 怎么测(§3) |
|---|---|---|
| 审查者发现错误的能力 | 认真的核验人单次核验发现错误的概率 ≈ **0.40**(`skill_honest=0.8` × 平均隐蔽度 0.5);不认真的 ≈ 0.15 | 埋错:混进带已知错误的版本,看被判「需修改」的比例 |
| 担保人把关的严格程度 | 诚实担保人识破作恶申请人的概率 **0.5**(`screen_skill`) | 按邀请人汇总被邀请者的核验准确率(只能测到代理量,见 §6) |
| 攻击者能走多远 | 新加入者中作恶者 **10%**、不认真者 **25%** | 红队:少数账户按剧本发错误内容、互相通过 |

推演的边际收益已经在下降,再仿真下去只是在假设上加假设。**试运行的目的就是把这三个数测出来,回到仿真里校准**。
两个起步领域互为对照(VISION §4c):大模型应用开发「对错容易检验」,运动健身「原理稳定但效果因人而异」,
同一套方法在两个领域测出的差距本身就是结论。

## 2. 现状(基线,2026-11-21)

用 `python3 tools/pilot_metrics.py --rpc https://blockchain.yeying.pub/rpc --site https://blockchain.yeying.pub` 测得:

| 领域 | 发布的版本 | 有独立核验 | 首次核验等待(中位数) |
|---|---|---|---|
| 大模型应用开发 | 17 | **0/17** | — |
| 运动健身 | 8 | 3/8 | ≈ 24 小时 |

被指派的核验人完成率 3/25(12%)。成员 2 人。**瓶颈是人,不是代码**:新成员加入的全流程现在只用钱包就能走完
(创建账户 → 复制公钥 → 被邀请 → 核验),试运行可以直接用。

## 3. 怎么测

### 3.1 埋错(测「发现错误的能力」)

- 组织者用一个**专用账户**(不参与核验)在两个领域各发布 **6 个埋错版本**,混在正常内容里。核验人不知道哪些是埋的。
- 错误要**像真的会犯的错**,按难易分三档,每档各 2 个:
  - 明显:数字或结论写反(例如把「组间休息 2–3 分钟」写成「10 秒」;把上下文窗口的单位写错);
  - 需要查证:出处与原文不符、条件被悄悄放宽(「适用于所有人」);
  - 需要动手:大模型领域给一段**跑起来结果不对**的示例代码;健身领域漏掉一条禁忌。
- **安全边界**:健身领域的埋错**不得**是会导致受伤的建议(不写错误的动作要领、不删除安全警告),
  只埋数字、出处、表述层面的错;对应单元正文末尾照常标「模型生成、待核验」。
- **先承诺、后公开**(两份文件,都放在 `.pilot/`,不进 git):
  1. **埋错清单** `plants.json`:每处埋错在哪个单元、原文是什么、改成什么。它在发布**之前**定稿,
     试运行开始时公布它的 SHA-256;
  2. **答案文件** `key.json`:由 `tools/pilot_plant.py --publish` 在埋错**发布之后**写出,带链上的实际版本号
     (版本号在发布前不知道,所以不能提前承诺)。

  结束时两份都公开。核对方法:先核对 `plants.json` 的哈希与开始时公布的一致;再从链上核对 `key.json` 里的每个版本,
  它的正文确实就是前一版正文做了清单里那几处替换——这样组织者既改不了清单,也编不出不存在的版本。
- **同一单元的几处埋错合成一个版本**(否则会出现只含一部分埋错的中间版本,核验了中间版本的人会按不完整的答案打分)。
  每处埋错的原文必须在正文里**恰好出现一次**,工具会拒绝改到核验要点里的同样字句。
- 结束后组织者为每个埋错版本**发布更正版本**,并在答案公开时说明;链上历史保留(版本不可改),但当前版本是正确的。

**读数**:每个领域「埋错版本被发现的比例」「埋错版本上单次核验判需修改的比例」(直接对应仿真的单次发现率)、
「干净版本被误判需修改的比例」(误报,仿真里没有,要补进模型);每位核验人的命中与误报。

### 3.2 担保(测「把关严格程度」的代理量)

按邀请人汇总:邀请了几人、几人真的参与核验、被邀请者在埋错版本上的命中率。
**诚实的局限**:小规模、熟人之间的试运行里,几乎不会有人邀请明知不可靠的人,
所以测不到「识破作恶申请人」的概率本身,只能看到「担保人带进来的人质量如何」。§6 会说明这一点。

### 3.3 红队(测「攻击者能走多远」)

- 2 个红队账户,只有组织者知道身份(写在答案文件里),由组织者邀请。
- 剧本:发布**看似可信但有错**的单元;两个红队账户互相核验「通过」;对诚实成员的正确单元判「需修改」。
- 规则同 3.1 的安全边界,结束时同样公开并更正。

**读数**:红队版本里有几个在诚实核验中「通过多于需修改」(逃过);红队互相通过了几次;
被诚实核验人抓到时已经过去多久。这测的不是「攻击者占比」(试运行里是组织者定的),而是
**在当前机制下,一个协调的小团伙能撑多久**。

### 3.4 运转

每个领域的核验覆盖、首次核验等待、被指派者完成率、每位核验人的核验量。这些不需要答案文件,随时可以算,
用来在试运行中途发现「没人核验」之类的问题并及时调整。

## 4. 规模与时间

| | |
|---|---|
| 核验人 | 每个领域至少 **3 人**,合计 6 人以上(到 6 人时核验人指派可以改成强制规则,见 VISION) |
| 时长 | 4 周 |
| 第 0 周 | 招募与邀请(新成员按 `testnet/MEMBERS.md` 在钱包里创建账户);准备埋错与红队内容;公布答案哈希;记下开始高度 |
| 第 1–3 周 | 正常运行:成员按「先核验这些」的顺序核验,也可以写新单元;每周用 `pilot_metrics.py --since-height <开始高度>` 看运转指标 |
| 第 4 周 | 公开答案文件,算全部指标;发布更正版本;把三个读数代回 `sim/convergence.py` 重跑,写结论 |

招募对象:大模型领域找写代码的开发者(能把示例跑起来);健身领域找有训练经验的人或教练。
两个领域的核验人按**同一套核验方法**核验(读核验要点 → 逐条核对出处 → 对数字 → 安全 / 可验证 → 给结论并写说明),
指南见 `testnet/REVIEWER-GUIDE-LLM.md` 与 `testnet/REVIEWER-GUIDE-FITNESS.md`。方法一致,两个领域的读数才能比较。
核验人不需要提前知道试运行在测什么,但**要事先告知**「试运行期间会有故意埋入的错误,结束时公开」——
不告知就是在欺骗参与者。

## 5. 结束后怎么用读数

1. 把两个领域的单次发现率、误报率、担保代理量代回 `sim/convergence.py` 的 `skill_honest`、`subtlety`、`screen_skill`,
   重跑第四轮的场景,看结论是否还成立(尤其是 §4b「最坏攻击者下的边界约 10%」);
2. 如果某个领域的发现率明显低于 0.40,说明那个领域需要更强的核验要点模板或更多核验人,而不是改共识;
3. 读数与结论写进 VISION 讨论记录与 `sim/CONVERGENCE.md`。

## 6. 这次试运行测不到什么

- **攻击者的真实比例**:试运行里由组织者决定,测不到;
- **担保人识破作恶申请人的能力**:熟人试运行几乎没有作恶申请人,只能测到代理量;
- **长期行为**:信誉衰减、见习期满后的行为变化,4 周太短;
- **统计显著性**:每个领域 6 个埋错、3 位核验人,样本很小,读数是「数量级」而不是精确值。
  宁可如实写「0.3 左右,样本 18 次核验」,也不要报一个看起来精确的数。

## 5.1 流程演练(先在本地走通,再上真实试运行)

`testnet/pilot-drill.sh` 在本机 4 节点 + 6 个成员账户上,把试运行要走的一整遍走通:
承诺清单的 SHA-256 → 发布埋错 → 协议指派 → 核验 → 确立与得分 → 结算 → 指标读出 → 发布更正。

它同时是**工具的验收**:每一步都有断言,不是"跑完就算"。演练里断言的东西:
埋错必须能干净地应用(原文恰好出现一次)、单元要在**经济激活之后**发布(否则不进经济、没有链上指派)、
指标算出的发现率与演练里安排的一致、**篡改过的答案文件必须被拒绝**。

演练中修掉的两个真问题:
- **单元必须在激活后发布**。激活前发布的版本链上没有指派记录,核验不计入、也不得分——
  演练里第一次就是踩了这个坑。
- **承诺核对的文件搞错了**(`tools/pilot_metrics.py`):承诺的是**埋错清单 plants.json**
  (发布前定稿),而工具去核对的是**答案文件 key.json**(发布后才有版本号),于是永远对不上。
  现在分两步:① 清单的 SHA-256 等于公布的承诺;② 答案文件里每个埋错版本的正文,
  确实等于前一版正文按清单做了那几处替换——从链上与正文仓库逐个重算。
  第二步防的是"组织者事后挑一个恰好有人判了需修改的版本,声称那就是埋错"。

  如果要更早开始,只能测"见习期内能不能核验"(核验照常记录),测不出可信度与报酬的效果。

## 7. 需要决定的事

1. **找谁**:每个领域至少 3 位核验人。截至 2026-11-25,测试网有 8 位成员,其中 2 位已过见习期;其余成员将在 11-30 至 12-02 陆续满期。详见 §6.1。
2. **埋错与红队要不要做**:它们是测出前两个参数的唯一办法,但会在测试网上留下(已更正的)错误版本历史,
   而测试网数据将来会作为主网启动数据(VISION §4d)。可选:只做埋错不做红队;或者迁移主网时排除这些版本。
3. **谁当组织者**:埋错内容由组织者准备,组织者不能同时当核验人。
